    Servlets

    The servlet contract: what a module must provide to serve routes.

    A servlet is a module with -behaviour(blizanci_servlet), named in a route (see the Routing chapter) and in the configured list of servlets. The three servlets shipped are blizanci_static (files, with no worker), blizanci_cgi and blizanci_titan (both with a worker in a ppool queue). The contract has three layers, which the behaviour declares in this order: the module contract, the servlet process contract, and the gateway contract.

    • Routing

    1. The module contract

    What the servlet MODULE provides. These callbacks are called in the context of whoever calls them, or at configuration time; no servlet process exists yet.

    • default_options/0 and validate_options/1 are called when a route is built (blizanci_router:build_route/5, from the configuration check and apply, in the process doing that). The route's own options are merged over default_options/0 (the route's win), the result is passed to validate_options/1, and that merged map is what the route keeps and passes to every later call as RouteOpts. A {error, Reason} from validate_options/1 refuses the whole routing table. It is the place to reject a bad configuration (say, a docroot that is not a directory) at start-up, not per request.
    • start/0 and stop/0 are called by the blizanci_servlets process: start/0 at application start and, on blizanci_config:apply/1, for servlets newly listed; stop/0 at application stop and for servlets no longer listed. They set up and tear down shared resources, such as the ppool queue of blizanci_cgi and blizanci_titan, so that nothing is left running (for example leaked ppool pools) across a stop/start cycle in the same VM. start/0 may return {error, Reason} (or raise, in which case Reason is {Class, Term}); the servlet is then not started, nor are any others in the same start-up or apply, and those already started are stopped again. start/0 must be harmless if the resource is already running; stop/0 should return ok. If it returns anything else, or raises, a warning is logged and it is otherwise ignored: the servlet is treated as stopped, the other servlets are still stopped, and nothing crashes.
    • request/4 is called once per request that the router has matched to a route of the servlet and authorised. It runs in the process of the connection (blizanci_connection), via blizanci_servlet_container:request/5, before any servlet process is created, so it should not block for long. It answers {immediate, Response}, a gemini_response() sent to the client as it stands, or defer, which hands the request to the process contract below.

    A servlet with no worker, such as blizanci_static, does all its work in request/4 and always answers immediate. It need only implement the callbacks of parts 2 and 3 trivially: serve/4 is never called (it may return {gateway_error, unimplemented}), handle_client_data/2 may return none, and cancel/1 may return ok. Conversely a servlet that always defers, as blizanci_cgi and blizanci_titan do, has a trivial request/4 returning defer. A servlet is unlikely to need a substantive implementation of both request/4 and serve/4, since it will behave either wholly synchronously or wholly asynchronously.

    The inputs

    request/4 and serve/4 take the same four arguments: Matches, Request, ServerConfig and RouteOpts.

    • Matches, a path_matches() map from binary to binary. The router matches the route's regular expression (anchored, except for an old-format route) against the request path, or a mount against its start; Matches holds what each NAMED group of the regular expression captured, keyed by the group's name, and FULL_PATH, the whole request path (for a mount, PATH is what follows the mount); a group that took no part in the match gives <<>>. The path matched is the decoded one: leading slash removed, percent-escapes decoded, normalised, and known to contain no "..". The router refuses at route build time any regular expression with no group named PATH, so PATH is always present, whatever the servlet; it is the path the servlet resolves under its own root (see blizanci_path:resolve_request/3). Other named groups pass through unchanged (CGI reads PATH_INFO this way).
    • Request, a request_details() map with keys client_cert (the raw peer certificate, or an error), query (the query string), rest_of_input (whatever the client sent after the request line in the same read, <<>> if nothing; Titan takes the start of the upload body from it), scheme and host (lower-cased), port and path (the request path as sent, before the decoding described above).
    • ServerConfig, the server_config() record of the site serving the request: hostname, port and routing (its list of routes). blizanci_cgi takes the server name and port from it; blizanci_static and blizanci_titan ignore it.
    • RouteOpts, the route's options map, merged with the defaults and validated as described above. The contents are the servlet's own; for example docroot, index, bare_mimetype and unknown_mimetype for blizanci_static, cgiroot and cgiprefix for blizanci_cgi, docroot and work_dir for blizanci_titan. The router does not interpret them.

    2. The servlet process contract

    What the servlet does in the CONTAINER process, once request/4 has answered defer. blizanci_servlet_container:request/5 then starts and links a new process, a blizanci_servlet_container (the "container"), and the connection traps exits to hear of its end. The servlet's worker, if any, is a further process, started by serve/4 (blizanci_cgi and blizanci_titan use a ppool queue); how it and the container talk is the gateway contract, part 3.

    serve/4 is called once, in the container process, straight after the container has told the connection it has started (so the connection is not held up by it, but the container is busy until it returns). It returns one of:

    • {gateway_finished, Response}: done; the container exits and Response, a gemini_response(), goes to the client as it stands.
    • {gateway_error, Reason}: the request failed. A Reason which blizanci_status maps to a failure status (for example file_not_found gives 51, gateway_busy 40) is sent to the client as that status; any other Reason is logged and the client gets an internal error (40).
    • {gateway_started, Pid}: the work continues in Pid, the worker, and the container stays alive, waiting for it. Pid is what the container later gives to handle_client_data/2 and cancel/1.

    (gateway_output, also a gateway_result(), is not a valid return from serve/4: the container would crash and the client get an internal error. This is documented as invalid, not endorsed.)

    3. The gateway contract

    The protocol between the container and the worker (the "gateway") which serve/4 started, once it has returned {gateway_started, Pid}. The container is then a gen_server (blizanci_servlet_container) which the connection and the worker talk to, and it remembers Pid and the servlet module. The worker's own messages are hidden behind the servlet module, as a gen_server module hides its protocol: the container never sends the worker anything but through the callbacks below.

    Container to worker, through the servlet module:

    • handle_client_data/2 is called in the container process, once the worker has started, with the client's further input (for example a Titan upload body) as the connection receives it, and the worker's Pid. It returns the gemini_response() to send to the client, or none if more is awaited. If it raises, the container is stopped and the client gets an internal error. A servlet which takes no further input returns none.
    • cancel/1 is called in the container process when the connection is shutting down before the work is over (for example the client hung up), with the worker's Pid. It should check that Pid is still a live process, and promptly stop it. The container then stops. It is not called if serve/4 did not return gateway_started.

    Worker to container, which is NOT a callback: the cast blizanci_servlet_container:gateway_exit(ContainerPid, Result). A worker which does not answer through handle_client_data/2 must itself report how it ended, exactly once, by calling blizanci_servlet_container:gateway_exit/2 with the container's pid (the pid of the process that called serve/4, which the worker has to be given) and one of {gateway_output, Binary}, the finished response as the script produced it, or {gateway_error, Reason}, treated as for serve/4. gateway_exit/2 is a cast, harmless if the container has gone. The container turns the report into a message to the connection, which answers the client and closes the connection. A worker that never reports leaves the client waiting for the connection's own timeout.

    Who runs what

    callback              layer    process                  when
default_options/0     1 module route builder            config, apply
validate_options/1    1 module route builder            config, apply
start/0               1 module blizanci_servlets        start, apply
stop/0                1 module blizanci_servlets        stop, apply
request/4             1 module connection               each request
serve/4               2 proc   container (new, linked)  after defer
handle_client_data/2  3 gway   container                later input
cancel/1              3 gway   container                conn closing

    Known limits

    This section describes the current behaviour, which may change.

    There are two reply paths, as the code stands. CGI-style workers (blizanci_cgi) report with gateway_exit/2, and handle_client_data/2 returns none. blizanci_titan never calls gateway_exit/2: it answers its client through the return value of handle_client_data/2, which is none while more data is awaited and the response once the upload is over.

    Not every gateway_result() is valid on every path. The container has no case clause for some, and would crash (the client getting an internal error). Invalid on the serve/4 path (part 2): {gateway_output, Binary}. Invalid as the argument of gateway_exit/2: {gateway_finished, Response} and {gateway_started, Pid}; only {gateway_output, Binary} and {gateway_error, Reason} are valid there. These are documented as invalid, not endorsed: the gateway_result() type is wider than either use.

    The container, for one request

    The module blizanci_servlet_container is the process side of the contract above: a servlet module's request/4 is called here, and, if it defers, a container process is started to run its serve/4. This is the servlet process contract (part 2), and, once serve/4 has started a worker, the container's side of the gateway contract (part 3). What goes on, for one request:

    • blizanci_router calls blizanci_servlet_container:request/5 in the connection process (blizanci_connection). This calls Module:request/4 there. An {immediate, Response} is returned as it stands.
    • On defer, defer_request/5 makes the connection trap exits and starts a new, linked container process with proc_lib:start_link/4 (two seconds allowed to start), returning {init_servlet, Pid}, after which the connection remembers Pid as its servlet process. (If the process did not start, the result is an internal-server-error code.) This sets things up for the results of the request to be notified back to the caller of request/5, which is a ranch handler for the Gemini protocol.
    • The container acknowledges at once, then calls Module:serve/4 in its own process. gateway_finished and gateway_error end the container here, with an exit reason {shutdown, {gateway_complete, Pid, Response}} or {shutdown, {gateway_init_error, Pid, Reason}}, which the connection, trapping exits, answers the client from. gateway_started turns the process into a gen_server (gen_server:enter_loop/3) whose state names the worker and the module.
    • The gen_server then handles three things. Client data: the connection calls handle_client_data/2, which calls Module:handle_client_data/2 with the worker's pid and returns what it returns. The worker's report: the worker calls gateway_exit/2 (a cast), and the container passes the result on to the connection by a gen_server:cast of {servlet_result, Result} (so the container never blocks on a connection which may itself be waiting on the container), where Result is {servlet_complete, Output :: binary()} or {servlet_failed, ErrorCode :: atom()}. Cancellation: when the connection ends it calls cancel/1, which casts servlet_quit; the container calls Module:cancel/1 with the worker's pid and stops.
