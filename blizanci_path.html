    confine(SubPath, Root)

    -spec confine(SubPath, Root) -> Result
                 when
                     SubPath :: binary(),
                     Root :: binary(),
                     Result :: {ok, binary()} | {error, file_not_found}.

    Join SubPath onto Root, canonicalise the result, and confine it to lie under Root -- the pattern shared by every servlet that resolves a request path against a configured root directory (CGI, static files, Titan uploads).

    File names are bytes. SubPath, Root and the result are all binaries, so the name that is checked is exactly the name that is opened. (Checking a string and opening it under another encoding once let a symlink named with a non-ASCII character lead out of the docroot.) The router converts the configured roots to binaries when a route is built (see blizanci_router); anything else as Root or SubPath is refused.

    Root is resolved to an absolute path first (via filename:absname/1), since fix_path/1 requires an absolute path and configured roots may be relative.

    Root itself is canonicalised too, not just absname'd, before being used as the confinement prefix: if Root sits behind a symlink (e.g. a blue/green deploy pattern such as docroot -> releases/v3), every legitimate resolved path would otherwise fail the prefix check, since Cmd is fully symlink-resolved but a bare absname'd Root would not be.

    A canonicalisation failure (e.g. a symlink loop tripping realpath's TTL guard) and a path which resolves outside Root are deliberately reported identically, as file_not_found: a remote client should not be able to use the response to distinguish "this doesn't exist" from "you tried to escape the root". The real reason is still logged.

    SubPath may contain any bytes except control characters: NUL, the other bytes below 16#20, and 16#7F (DEL) are refused. Bytes 16#80 and above are allowed, whether or not they form valid UTF-8. This is deliberately NOT a policy on which names are acceptable: invisible, bidirectional and look-alike characters (zero-width characters, bidi overrides and so on) pass through here, and are for the caller, in the URL layer, to refuse. Root is not restricted this way (it is the operator's), but may not contain NUL, which operating systems treat as the end of a name. Anything other than a binary as SubPath is refused.

    Hidden files are refused: any path segment beginning with a dot is denied (as file_not_found, so the response does not reveal whether the file exists), whatever the servlet. It is judged twice: on SubPath as given, so a symlink named ".env" is refused although it points at an ordinary file, and on the resolved path relative to Root, so a link to a dot-directory (say "pub" pointing at ".git") is refused although its own name is innocent. Only segments below Root count: a Root that itself lies under a dot-directory is fine. The one exception is a ".well-known" directory as the FIRST segment under Root, as RFC 8615 places it, and only when the caller asks for it with the option well_known (confine/3); a ".well-known" further down is an ordinary hidden directory, and a dotfile inside ".well-known" is still hidden. confine/2 allows no exception.

    path_under_root(S, Root)

    -spec path_under_root(S, Root) -> Result
                         when S :: string() | binary(), Root :: string() | binary(), Result :: boolean().

    Is the path S underneath Root (or Root itself)? S must equal Root, or begin with Root followed by a path separator: a bare string-prefix test would wrongly accept a sibling such as /srv/docs-secret for a Root of /srv/docs. S and Root are both strings or both binaries.

    It is (currently) the responsibility of the caller to canonicalise/normalise the paths before calling this function.

    • S: the path to check
    • Root: the directory under which S is supposed to be located
