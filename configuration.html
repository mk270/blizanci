    Configuration

    The configuration of a blizanci instance is built from the application environment (sys.config) at start-up, or from explicit values by the builder functions of the module blizanci_config (new/2, site/3, add_route/2 and so on).

    Currently, a config file is required. Create a sys.config file, for example in the config/ directory, in the format suggested in config/sys.config.example.

    How it is applied

    At start-up blizanci_config:from_app_env/0 builds the configuration and validates it, reporting every problem found in one pass as a list (see the section Start-up errors below); a bad configuration stops the application starting. A site's certificate and private key must be a matching pair, or the site is refused; a pair whose key type cannot be compared is accepted with a warning.

    The configuration is held in an ETS table owned by blizanci_conf_serv, the single source of truth, which is read by the TLS sni_fun and by each connection, and which blizanci_config:apply/1 replaces while the server runs. See the Internals chapter for the detail.

    A minimal configuration

    A minimal configuration serves one site, with one public route. The sites key lists the sites; each has a hostname, a certificate, a private key and a routing table. Nothing here is defaulted: the paths are yours to choose, and the certificate and key must be a matching pair that blizanci can read, or it will refuse to start:

    [{blizanci, [
   {sites, [
     {"example.org", [
       {certfile, "ssl/certificate.pem"},
       {keyfile, "ssl/key.pem"},
       {routing, [
         {mount, gemini, "/", blizanci_static, public,
          #{docroot => "./public_gemini"}}
       ]}]}
   ]}
 ]}].

    To keep a part of the site for holders of a client certificate, define a realm (a named set of CA certificates) in the top-level realms key and name it in a private route. Routes are tried in order, so the more specific mount comes first:

    [{blizanci, [
   {realms, [{<<"staff">>, ["ssl/staff-ca.pem"]}]},
   {sites, [
     {"example.org", [
       {certfile, "ssl/certificate.pem"},
       {keyfile, "ssl/key.pem"},
       {routing, [
         {mount, gemini, "/private", blizanci_static,
          {private, {realm, <<"staff">>}},
          #{docroot => "./public_gemini/private"}},
         {mount, gemini, "/", blizanci_static, public,
          #{docroot => "./public_gemini"}}
       ]}]}
   ]}
 ]}].

    config/sys.config.example is a fuller example. (The example vm.args is for a release, which is not available for now; the way of running blizanci described in the README does not read it.)

    Configuration items

    • {port, Port::integer()}: the port to listen on (defaults to 1965); 1 to 65535, so 0 is refused.
    • {realms, [{Name::binary(), [CACertPath::string()]}]}: authentication realms: named sets of CA certificates, global to all sites, used for verifying client certificates. See the Realms section of the Authorisation chapter.
    • {servlets, [Module::atom()]}: the servlets which routes may use (defaults to blizanci_static, blizanci_cgi and blizanci_titan).
    • {sites, [{Hostname::string(), [Option]}]}: the sites served on the port, at least one. See Sites, below.

    Relative paths are allowed in the configuration, including the docroot and cgiroot options of routing entries; the exception is the work_dir of a Titan route, which must be absolute (see the Titan chapter).

    Removed keys

    The old flat keys of the single-site form of earlier versions (hostname, certfile, keyfile, docroot, cgiroot, ca_certs, titan_work_dir and routing, at the top level of the blizanci section) are no longer supported: if any is set, with or without sites, start-up is refused with one error naming the ones found. Move them into an entry of the sites key.

    Sites

    The sites blizanci serves are set by the sites key. To serve several hostnames from one port, each with its own certificate and routes, give one entry for each:

    {blizanci, [
  {port, 1965},
  {sites, [
    {"a.example", [{certfile, "/srv/a/cert.pem"},
                   {keyfile, "/srv/a/key.pem"},
                   {routing, [{mount, gemini, "/", blizanci_static,
                               public, #{docroot => "/srv/a"}}]}]},
    {"b.example", [{certfile, "/srv/b/cert.pem"},
                   {keyfile, "/srv/b/key.pem"},
                   {routing, [{mount, gemini, "/", blizanci_static,
                               public, #{docroot => "/srv/b"}}]}]}
  ]}
]}

    The rules:

    • A site is {Hostname, Options}, and the hostname is a string. A site takes certfile (the path to the site's certificate), keyfile (the path to its private key) and routing, and nothing else; all three are required. There is no default routing table and there are no shorthand keys such as docroot or cgiroot. Every site spells out its own routes, and each route names its own root in its options (see the Routing chapter).
    • port and servlets are global, as is realms. A route in a site names realms defined in the global realms key.
    • The sites are told apart by SNI: the TLS server name picks the site. If the host in the request URL differs from the SNI name, the client gets status 53 (host unrecognised).
    • Hostnames are folded to lower case, so "A.Example" and "a.example" are the same name. The same name twice, after folding, is an error.
    • A site whose routes are all public does not ask clients for a certificate; a site with a restricted or private route does.
    • A site's certificate and key must be a matching pair (see Start-up errors, below).
    • Routing

    A worked example: a.example is a public static site, and b.example is a static site that also takes Titan uploads from clients holding a certificate signed by the CA in the realm staff:

    {blizanci, [
  {port, 1965},
  {realms, [{<<"staff">>, ["/srv/ssl/staff-ca.pem"]}]},
  {sites, [
    {"a.example", [
      {certfile, "/srv/a/cert.pem"},
      {keyfile, "/srv/a/key.pem"},
      {routing, [
        {mount, gemini, "/", blizanci_static, public,
         #{docroot => "/srv/a/gemini"}}
      ]}]},
    {"b.example", [
      {certfile, "/srv/b/cert.pem"},
      {keyfile, "/srv/b/key.pem"},
      {routing, [
        {mount, gemini, "/", blizanci_static, public,
         #{docroot => "/srv/b/gemini"}},
        {mount, titan, "/", blizanci_titan,
         {private, {realm, <<"staff">>}},
         #{docroot => "/srv/b/gemini",
           work_dir => "/srv/b/titan-work"}}
      ]}]}
  ]}
]}

    The warnings about old-format and shadowed routes (see the Routing chapter) are logged for each site's table, and in a multi-site configuration the line names the site, for example (one line in the log):

    routing: site b.example: route 2 (gemini mount "/docs") is
shadowed by route 1 (gemini mount "/") and is never used

    Directory options

    The directory options of a route (docroot, cgiroot and work_dir) may be written as a string or as a binary. They are converted to binaries once, when the route is built, and servlets only ever see binaries. Library callers that supply their own servlets must therefore expect a binary docroot, cgiroot and work_dir in their options.

    They must be plain ASCII file names (printable characters only, codes 32 to 126). Anything else is refused at start-up with an error that names the route and the option. Relative paths are kept as written. cgiprefix is a URL prefix, not a file name, and is not affected.

    Start-up errors

    At start-up blizanci checks the whole configuration and reports every problem it finds in one pass, not just the first. Each problem is one error-level log line starting "blizanci:" and naming the site or the route concerned, so you can fix them all before the next attempt. Start-up then fails. For example (these would not all occur together, and each is one line in the log):

    blizanci: site a.example: certificate /srv/a/cert.pem and private
key /srv/b/key.pem are not a matching pair
blizanci: site b.example: the required key certfile is missing
blizanci: port 0 is not a TCP port number (1 to 65535)
blizanci: the single-site keys hostname, certfile are no longer
supported; move them into an entry of the sites key
blizanci: no sites are configured; the sites key must list at least
one

    Other problems reported this way include a hostname that is not a string, a site configured twice, an unreadable or undecodable certificate or key file, a route that names an undefined realm or a servlet that is not in servlets, an invalid route, and a Titan work directory that is missing or on the wrong filesystem. The one-line text of each error is produced by blizanci_config:describe_error/1.

    For each site, the certificate and the private key must be a matching pair; otherwise every TLS handshake for that site would fail, so start-up is refused instead and the line names both files. If the key is of a type that cannot be compared with its certificate (DSA, for example), the pair is accepted with one warning (one line in the log):

    site a.example: cannot verify that certificate /srv/a/cert.pem and
private key /srv/a/key.pem are a pair (unsupported key type DSA)

    Warnings never stop start-up. They are: a shadowed route, a table that uses the old route format, and a pair that could not be verified.
