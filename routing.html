    Routing

    Each site has one routing table: an ordered list of routes. A request is matched against the routes for its protocol (gemini or titan) in order, and the first route that matches serves it. A route serves exactly one protocol, so a static site that also takes Titan uploads needs a gemini route and a titan route. If no route matches, the client gets "not found". The table is the routing key of the site, in sys.config (see the Configuration chapter); there is no default table.

    Routes are prepared by blizanci_router:prepare/3, which checks that each entry is valid. An error names the route: {bad_route, Index, Kind, Reason}, where Index is the 1-based position in the list, Kind is mount, regex, tuple (the old format) or unknown, and Reason says what is wrong. At start-up, blizanci_router:prepare_all/3 is used instead: it reports every problem at once, building every route and returning those that built along with an error for each one that did not, in order. Warnings are logged only when every route built.

    Route kinds

    A route is one of two tagged tuples:

    {mount, Proto, Path,  Module, Auth, Opts}
{regex, Proto, Re,    Module, Auth, Opts}

    Proto is gemini or titan. Module is the servlet, e.g. blizanci_static, blizanci_cgi or blizanci_titan. Auth is the authorisation policy (see the Authorisation chapter), and Opts is the servlet's options map, such as #{docroot => "./public_gemini"}. Each route names its own root directory in Opts. Request paths here are the decoded ones, without the leading slash.

    Mounts

    A mount selects requests by path prefix, in whole path segments. The mount "/docs" (or "/docs/", which is the same) matches /docs, /docs/ and /docs/a.gmi, but not /docsx/a.gmi. The mount "/" matches everything, being the whole site.

    The validator requires a mount path to be a non-empty string (or binary, UTF-8) that starts with "/". It may have no empty segment (so no "//"), though one trailing "/" is allowed and ignored. It may have no "." or ".." segment. Only printable ASCII (codes 32 to 126) is allowed: no control character and nothing non-ASCII, as a request path is always printable ASCII once decoded.

    What the servlet receives:

    • PATH, the remainder of the request path after the mount, with no leading slash. For mount /docs and request /docs/a/b.gmi, PATH is a/b.gmi; for the request /docs itself it is empty. This is the path the servlet resolves under its own root, so a mount's Opts must name the directory that corresponds to the mount, not the site's whole document root.
    • FULL_PATH, the full request path as the router sees it (decoded and normalised), with no leading slash: docs/a/b.gmi in the example.

    Regex routes

    A regex route selects requests with a regular expression (Erlang re, i.e. PCRE) that must match the whole request path: blizanci anchors it itself, by wrapping it in \A(?:...)\z, so "docs/(?<PATH>.*)" does not match x/docs/a.gmi. The path matched has no leading slash. The regex must have a named group PATH, which is what the servlet resolves under its root, and may not have one named FULL_PATH. Other named groups pass through to the servlet (CGI reads PATH_INFO this way). FULL_PATH is supplied as for mounts. In (?x) mode, avoid a trailing # comment, as the anchoring text is appended to the pattern and a trailing comment will not compile.

    Old-format routes

    The old 5-tuple, {Proto, Regex, Module, Auth, Opts}, is still supported, and there is no plan to remove it. It is translated to the new format and behaves exactly as before: its regex is NOT anchored but searched for anywhere in the path, and it must have a PATH group. It also receives FULL_PATH (unless its own regex has a group of that name). If any route in the table uses the old format, one line is logged at start-up, at warning level:

    routing: 5 routes use the old tuple format {Proto, Regex, Module,
Auth, Opts}; translated, behaviour unchanged (see manual, Routing)

    (the count varies; in a multi-site configuration the line also names the site). New-format routes never trigger it. Rewrite the routes as mounts or anchored regexes to silence it; note that unanchored "(?<PATH>private.*)" also matches docs/private/x.gmi, which an anchored regex or a mount would not.

    Old 5-tuple routes may still use {private, CAFiles} as their authorisation policy; see the Authorisation chapter.

    Shadowing

    When the table is built, blizanci checks for routes that can never be used because an earlier route of the same protocol (gemini routes are compared only with gemini routes, titan with titan) matches every request they could. This only warns, and never refuses a table, stops start-up or changes routing. One warning is logged per shadowed route, naming it and the first route shadowing it by position and kind, and by mount path or regex, for example:

    routing: route 2 (gemini mount "/docs") is shadowed by route 1
(gemini mount "/") and is never used

    The check can be turned off with the option warn_shadowed (default true) of blizanci_router:prepare/3. Authorisation policies are not considered. The rules are:

    Mount against mount is exact: the earlier mount shadows the later if its segments are a prefix of the later one's segments, so "/" shadows every later mount, and so does an equal mount, but "/docs" does not shadow "/docsx".

    Whenever a regex is involved (as either route, old-format or not) overlap cannot be decided, so it is probed, and a false negative is preferred to a false positive: the check can miss a shadowed route but should not report a false one. Sample paths are derived from the later route: for a mount M, M itself, M/x and M/a/b; for a regex, the literal text its source starts with (a leading ^ skipped, the text cut short before a quantifier, and none at all if the source has a vertical bar), L, plus L followed by x, a/b and x.gmi. Only samples that the later route itself matches are kept, and with fewer than two of them nothing is reported. The earlier route is then run on every sample with the router's own selector, and the later route is reported only if the earlier one matches all of them. A partial overlap is never reported.

    Example: a routing table

    A table with protected areas: /private for clients with certificates from the realm staff, and /restricted for any client with a certificate. Each mount names its own subdirectory as its root, and the more specific mounts come before "/":

    {routing, [
  {mount, gemini, "/cgi-bin", blizanci_cgi, public,
   #{cgiroot => "./cgi-bin"}},
  {mount, gemini, "/private", blizanci_static,
   {private, {realm, <<"staff">>}},
   #{docroot => "./public_gemini/private"}},
  {mount, gemini, "/restricted", blizanci_static, restricted,
   #{docroot => "./public_gemini/restricted"}},
  {mount, gemini, "/", blizanci_static, public,
   #{docroot => "./public_gemini"}},
  {mount, titan, "/", blizanci_titan,
   {private, {realm, <<"staff">>}},
   #{docroot => "./public_gemini", work_dir => "/srv/titan-work"}}
]}

    The realm staff must be defined in the top-level realms key. Relative paths are allowed in docroot, cgiroot and work_dir (a Titan work_dir must still be absolute; see the Titan chapter). Without the /private and /restricted routes, the "/" route would serve those directories publicly.

    Dispatch

    blizanci_router:route/4 takes the protocol (gemini or similar), the request path, the request and the server configuration, whose routing table is the ordered list of routes. It searches for whether the request matches any of them, and if so dispatches it to the servlet module of the route, through blizanci_servlet_container:request/5. See the Servlets chapter.
